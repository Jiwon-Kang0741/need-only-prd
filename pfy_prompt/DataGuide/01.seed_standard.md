## 1.5 SPEC 기계 추출·Codegen 정렬

* 백엔드 코드젠(`DataEngineerAgent`)은 SPEC 본문에서 **`## 7.`으로 시작하는 첫 줄**을 찾고, 그 **다음에 등장하는 `##` + 숫자** 헤딩 직전까지를 잘라 “Section 7” 블록으로 프롬프트에 주입한다. (`agents.py`의 `_extract_markdown_section(..., "## 7.")`와 동일)
* **주의 — SPEC 파일 종류와의 관계**: `spec.example.md`(채워진 예)만 있고 `## 7.0`이 없는 경우, `# 7`은 **Business Rules**이고 첫 `## 7.1`만 잡힐 수 있다. **`spec.template.md`에는 `## 7.0 DB Seed & codegen alignment`가 포함**되어 있어 동일 추출 로직으로 시드 요약이 주입 블록에 들어간다. **DB 시드 메타 표는 `# 10. Seed Metadata`**를 SSOT로 둔다.
* 따라서 “시드 규칙이 SPEC에서 LLM으로 확실히 전달”되게 하려면 아래 **한 가지 이상**을 택한다.
  1. **SPEC에 시드 전용 `## 7.` 계열 헤딩을 둔다** — 예: 다른 `## 7.1`(업무 규칙)보다 **위에** `## 7. DB Seed Data` 또는 `## 7.0 …`처럼 `## 7.`으로 시작하는 줄을 두어, 추출 블록이 `cmn_*`·`pgm_url`·라벨 규칙 등을 담도록 한다. 또는
  2. **파이프라인을 수정**하여 `# 10. Seed Metadata`(또는 `## 10.`) 등 **실제 시드 메타가 있는 섹션**을 잘라 주입한다.
* LLM이 `spec.template.md`를 따른 출력에는 **`## 7.0`**이 포함되므로 시드 요약이 주입 블록에 포함되기 쉽다. **레거시 SPEC**(예: `## 7.0` 없이 `## 7.1`만 있는 경우)만 (1)(2) 없이 쓰면 주입 블록과 `# 10`이 **어긋날 수 있다.**

## 4.3 menu_id 규칙

menu_id는:

* unique
* immutable

이어야 한다.

**문자열 구성(권장·`menu_tree`/`cmn_menu` 정합):**  
`menu_id` = **`p_menu_id`**(= 부모 행의 `menu_id`, JSON에서는 `parentId`) **+** 같은 부모 아래에서의 **순번 접미**(숫자만, 예: `01`, `02`).  
예: `p_menu_id`=`ROOT02` 이고 형제 중 첫 프로그램이면 `menu_id`=`ROOT0201`(=`ROOT02`+`01`). **`menu` 등 임의 접두 + `0201`처럼 부모 ID와 무관한 네 자리를 붙이지 않는다.**

**`sort_num` / `cmn_menu.menu_sort` (`menu_tree.json` → 시드 생성 시):**  
`menu_id`에서 **`p_menu_id` 접두를 제거한 나머지(순번 접미)** 를 **10진 정수**로 해석한 값과 **`sortOrder` / `menu_sort`** 가 **일치**해야 한다(예: `ROOT0201` → 접미 `01` → **1**).  
`menu_id` 문자열에서 **`p_menu_id`를 빼지 않고** 잘라낸 `0201` 등을 `menu_sort`에 넣는 방식은 **금지**한다.

**운영 `CMN_MENU`와의 차이:** 레거시·운영 데이터는 아래 §4.4처럼 `MENU_SORT` 표기가 접미와 항상 1:1이 아닐 수 있다. **마이그레이션·조회 SQL은 실제 DDL·데이터 규칙을 따른다.**

자동 수정 금지.

---

## 4.4 운영 `CMN_MENU`·메뉴 트리 조회 (참고)

운영 DB에서는 `MENU_SORT`가 `'01'`, `'02'`, `'99'`, `'00'` 등 **문자/패딩**으로 저장되는 경우가 많다. 형제 간 정렬·비교에는 **`CAST(MENU_SORT AS INTEGER) AS SORT_NUM`**(또는 동등 식)을 쓰는 패턴이 일반적이다.

역할(`CMN_ROLE_MENU`)에 연결된 메뉴만 두고 부모를 `WITH RECURSIVE`로 거슬러 올린 뒤, 트리 출력 정렬은 흔히 아래 순서를 따른다.

* `ORDER BY LEVEL DESC, SORT_NUM, MENU_ID`

`menu_id`는 **`P_MENU_ID` + 접미** 형태가 계층 전반에 쓰인다(예: `ROOT0201`/`ROOT02`, `ROOT990101`/`ROOT9901`). 접미 자릿수·`MENU_SORT` 저장 방식은 **테이블·업무 규칙별로 다를 수 있으므로**, 시드·SPEC의 `menu_tree.json` 규칙(§4.3)과 **불일치하면 운영 DDL·기존 데이터를 SSOT**로 한다.

금지:

* PK 변경
* Natural Key 변경

---

## 6.3 DELETE 정책

Seed 데이터는 idempotent 재실행 가능해야 한다.

따라서 Seed 영역에서는 제한적 Hard Delete를 허용한다.

허용 대상:

* cmn_role_menu
* cmn_role_pgm
* 재생성 대상 mapping 데이터
* fallback 재생성 데이터

허용 방식:

* 대상 key 범위 DELETE 후 INSERT
* 또는 ON CONFLICT 기반 Upsert

금지:

* 업무 데이터 전체 삭제
* 무조건 DELETE 후 전체 INSERT
* WHERE 없는 DELETE

DELETE는 반드시 대상 범위를 명확히 제한해야 한다.

---

## 6.4 Seed Sync 정책

Seed 데이터는 선언형 상태 동기화(Declarative Sync)를 기준으로 관리한다.

동일 입력 기준:

* 동일 결과 상태 보장

허용:

* DELETE + INSERT
* ON CONFLICT UPDATE

목표:

* init.sql 반복 실행 가능
* 환경 간 동일 상태 보장
* role/menu 동기화 안정성 확보

# 7. 매핑 규칙

## 7.1 cmn_menu

| 컬럼        | 값                   |
| --------- | ------------------- |
| menu_id   | menu_tree.menu_id (`menuId`) |
| lbl_cd    | menu_tree.menu_id (`menuId`) |
| p_menu_id | **`menu_tree.parentId`** (JSON 키 이름; 부모 행의 `menu_id`, 예: `ROOT02`). **`componentKey`(예: `mon`)·`module` 슬러그와 혼동 금지 — `p_menu_id`에 넣으면 안 된다.** |
| menu_sort | `menu_tree.sortOrder` **이면서**, `menu_id`에서 `p_menu_id`(=`parentId`) 접두를 뺀 **순번 접미를 정수로 해석한 값**과 같아야 한다(예: `ROOT0201`/`ROOT02` → 접미 `01` → **1**). **`0201`처럼 접두 제거 없이 잘라 sort에 넣지 않는다.** — 신규·`menu_tree.json` 기반 시드에 적용. **레거시 `CMN_MENU`는 §4.4**(`MENU_SORT` 문자·`CAST`·정렬 패턴)를 따른다. |

> SPEC의 **`parent_menu_id`** 는 위 **`p_menu_id`와 동일**하게, `menu_tree`의 **`parentId`**(부모 행의 `menu_id`)를 적는다(예: `ROOT02`). **`componentKey`**(예: `mon`)는 **`p_menu_id`에 넣지 않는다.** 화면코드 LV2(Pascal `Mon`)·프론트 `module` 경로는 부모(또는 소속) **폴더 노드의 `componentKey`**에서 맞춘다. SPEC §10.1의 **`menu_component_key`** 가 그 슬러그를 기록한다.  
> **`menu_id`** 는 **`[parent_menu_id][순번접미]`** 형태로, 순번은 **`menu_id` 문자열에서 `parent_menu_id`(=`p_menu_id`)를 제외한 나머지**이며, **`cmn_menu.menu_sort`** 는 그 순번을 **정수**로 해석한 값(앞자리 0 제거 후)과 맞춘다.

## 7.3 cmn_lbl — 행 유형 두 가지

`cmn_lbl`에는 **서로 다른 Natural Key 공간**을 쓰는 두 종류의 행이 공존한다. §12의 “중복 lbl_cd” 검증은 `(lbl_cd, lang_cd)` 조합 기준이다.

### 7.3 A. 메뉴(네비게이션) 라벨 행

메뉴 트리·`cmn_menu` / `cmn_pgm`과 맞물리는 **메뉴 ID 기반** 라벨이다.

| 컬럼      | 값                 |
| ------- | ----------------- |
| lbl_cd  | menu_tree.menu_id |
| lbl_nm  | menu_tree.menu_nm |
| lang_cd | ko-KR             |

### 7.3 B. 화면 UI 라벨 행

화면 내부 SearchForm·DataTable 등의 문구용 행이다. **`lbl_cd`는 menu_id와 같지 않으며**, §16.2의 **`{program_id}.{대컴포넌트명}.{라벨ID}`** 패턴을 따른다. 여기서 **`{program_id}`는 `spec.md`(또는 동등 SPEC) `# 1` Screen Metadata 표에서 추출한 `program_id` 값**이다. §16.3의 `cmn_menu.lbl_cd` == `menu_id` == `cmn_pgm.lbl_cd` 관계는 **7.3 A 행**을 가리킨다; 7.3 B 행은 별도 `lbl_cd`로 추가한다.

# 16. 시스템 공통 Seed Data 정합성 규칙
- Seed 데이터 생성을 위해 데이터 엔지니어 에이전트가 관리하는 시스템 공통 테이블은 **`cmn_class` → `cmn_code`(해당 시) → `cmn_lbl` → `cmn_pgm` → `cmn_menu` → `cmn_role_pgm` → `cmn_role_menu`** 순서로 DDL 및 INSERT(또는 UPSERT) 문을 생성해야 한다. (`# 10.3` 공통코드가 없으면 **`cmn_lbl`부터** 동일 순서.)
- 모든 시드 데이터 업데이트는 PostgreSQL에 안전한 **`INSERT ... ON CONFLICT ... DO UPDATE`** 구문을 사용한다.

## 16.1 pgm_url 변환 규칙
`cmn_pgm.pgm_url` 필드는 계획된 프론트엔드 Vue 파일 경로로부터 아래의 **정량적 치환 공식**을 엄격히 적용한다.
- **소스 경로 패턴**: `src/pages/{module}/{category}/{screenId}/index.vue`
- **변환 URL 패턴**: `/pages/{module}/{category}/{screenId}/index.vue`
- **제약 조건**: 
  1. 모든 역슬래시(`\`)는 슬래시(`/`)로 통합 치환한다.
  2. 기두의 `src/`는 제거하고 무조건 `/`로 시작하는 루트 경로 형태를 유지한다. 경로 컨텍스트 누락 시 §1.3에 의거하여 즉시 중단한다.

## 16.2 cmn_lbl (화면 UI 라벨) ID 생성 규칙
화면 내부의 컴포넌트 라벨 데이터를 `cmn_lbl`에 적재할 때는 아래 패턴을 강제한다. (행 종류 구분은 §7.3 B 참고)

- **lbl_cd 패턴**: `{program_id}.{대컴포넌트명}.{라벨ID}`
- **규칙**: 
  1. `{program_id}`는 SPEC `# 1` Screen Metadata의 **`program_id`** 열과 **동일 표기**여야 한다. (`screen_id`·폴더 PascalCase를 `lbl_cd` 접두에 쓰지 않는다.)
  2. `{대컴포넌트명}`은 유추가 아니라 실제 생성될 프론트엔드 폴더·컴포넌트 명과 **완전 일치**해야 한다. (예: `SearchForm`, `DataTable`, `SumGrid`)
  3. `lang_cd` 기본값은 항상 `'ko-KR'`로 고정한다.
  4. *예시: `CPMSMONRISKLST.SearchForm.searchDate`* (`CPMSMONRISKLST` = SPEC `program_id`)
- **Vue i18n**: 템플릿에서는 `t('{대컴포넌트명}.{라벨ID}')` 형태를 쓴다(`program_id` 접두 없음). DB `lbl_cd`와의 대응은 SPEC·FRONT_UI_STANDARD에 맞춘다.
- **정적 검증·대소문자**: 코드젠 쪽 `db_init_sql` 검증은 SQL 본문을 소문자로 비교하는 경우가 있어, `lbl_cd` 문자열에 `SearchForm.`·`DataTable.` 등 **PascalCase**를 사용해도 된다(소문자 변환 후 `searchform.` 등 마커와 일치하면 통과). **의도적으로 다른 케이스만 쓰지 말 것**(실제 생성 컴포넌트명과 불일치 방지).

## 16.3 메뉴 및 프로그램 상호 참조(ID) 일관성 규칙
공통 테이블 간의 참조 무결성을 위해 하라문(ID) 관계를 강제로 통일한다.
- **동일 패턴 유지**: `cmn_menu.lbl_cd` == `menu_id` == `cmn_pgm.lbl_cd` 관계가 성립하도록 식별자를 결합해야 하며, 상위 `cmn_lbl.lbl_cd`에 해당 값이 반드시 존재해야 한다.
- **상위 메뉴 ID Fallback**: `SPEC.md`에 상위 메뉴 컨텍스트(`p_menu_id`)가 누락되었을 경우, 임의 추론을 금지하고 기본값으로 `'ROOT98'`을 적용하며, `menu_id`는 `'ROOT98_YYMMDD_NNN'` 패턴으로 대체 생성한다.
- **권한 매핑 가드레일**: `DEV_AUTO` 권한 롤 매핑 데이터는 중복 데이터가 발생하지 않도록 제어하여 `cmn_role_pgm` 및 `cmn_role_menu` 양측에 모두 누락 없이 인서트한다.

## 16.4 Mockup 유도 `cmn_class` / `cmn_code` (선택)

**입력 SSOT**: SPEC `# 10.3 Mockup-derived Common Code` 표. Mockup에서 **`SearchFormField`의 `name`** = **`cls_id`**(= 표의 `class_cd`), **`SearchFormLabel`** 등 = **`cls_nm`**(= `class_nm`), Select **`optionValue` / `optionLabel`** = **`code_cd` / `code_nm`**.

**DB 매핑 (`테이블정보.md` 기준)**  
- `cmn_class`: `lang_cd='ko-KR'`, `cls_id`, `cls_nm`, `cls_desc`(보통 `cls_nm`과 동일), `cls_sort`(`'1'` 등 VARCHAR), `use_yn='Y'`, `lbl_cd`는 **NULL**, 감사 컬럼은 §10 공통.  
- `cmn_code`: `cls_id`, `code_cd`, **`code_desc`에 SPEC의 `code_nm`(표시문) 저장**, `code_sort`는 옵션 순서대로 **`'1'`,`'2'`,…** (컬럼 타입 VARCHAR), `p_cls_id`·`p_code_cd`·`lbl_cd`는 **NULL**(평면 코드), `use_yn='Y'`, 감사 컬럼 §10. **`code_nm`/`lang_cd` 컬럼이 실제 DDL에 존재하면** 그 DDL을 따른다(본 문서는 테이블정보에 없는 경우 `code_desc` 매핑을 기본으로 한다).

**스키마**: 배포 DDL의 스키마·`search_path`를 따른다. 문서 예시에만 `pfyown.` 등을 붙이지 말고, **실제 생성 SQL은 프로젝트 표준 한 가지로 통일**한다.

**멱등성**: `cmn_lbl` 등과 동일하게 **`INSERT ... ON CONFLICT ... DO UPDATE`** 를 사용한다. `ON CONFLICT` 대상 컬럼은 **배포 DDL의 PK·UNIQUE**에 맞춘다(예: `(lang_cd, cls_id)` / `(cls_id, code_cd)` 등 — DDL 미확인 시 생성 중단).

**예시 (컬럼만 참고; CONFLICT 절은 DDL에 맞게 조정)**:

```sql
INSERT INTO cmn_class (lang_cd, cls_id, cls_nm, cls_desc, cls_sort, lbl_cd, use_yn, insert_uid, insert_dt, update_uid, update_dt)
VALUES ('ko-KR', 'riskGrdCd', '리스크 등급', '리스크 등급', '1', NULL, 'Y', 'SYSTEM', now(), 'SYSTEM', now());

INSERT INTO cmn_code (cls_id, code_cd, p_cls_id, p_code_cd, lbl_cd, code_desc, code_sort, use_yn, insert_uid, insert_dt, update_uid, update_dt)
VALUES ('riskGrdCd', 'L', NULL, NULL, NULL, 'Low', '1', 'Y', 'SYSTEM', now(), 'SYSTEM', now());
```
